# ADR-058: Поставка образов на закрытый сервер

**Date:** 2026-11-08  
**Status:** Proposed  
**Normative parent:** [MODELING_ARCHITECTURE.md](../architecture/MODELING_ARCHITECTURE.md)  
**Related:** [ADR-002](ADR-002-git-published-source.md), [ADR-004](ADR-004-modular-monolith.md), [ADR-012](ADR-012-semantic-diff-review.md)  
**Precedent (not a dependency):** `moex-prodata-platform` [ADR-0044](../../../moex-prodata-platform/docs/adr/ADR-0044-airgap-image-deploy.md)

## Context

Рабочий сервер запускает служебный интерфейс (`apps/api`), веб-приложение (`apps/web`) и просмотр модели (`apps/viewer`). На этом сервере нет выхода в интернет за базовыми образами, пакетами Python и npm, и нет общего git с машиной разработки. Локальный GitLab есть: в нём должны лежать сами модели.

До серии образа приложений не было. Был только `apps/drawdb/Dockerfile`, и drawDB в эту поставку не входит. Служебный интерфейс слушал `127.0.0.1:8000`. Корень данных он искал по файлу схемы DAMS и читал модели как файлы рабочей копии. Адаптер Git умел локальную копию и GitHub, GitLab API не было. Это состояние на момент решения. Сейчас в репозитории есть образы, compose, скрипты поставки, провайдер GitLab и сверка копии моделей с контрактами образа (шаги PR-0…PR-4 в D6).

Опубликованная модель остаётся ревизией Git (ADR-002). Класть файлы моделей внутрь образа программ смешает два канала обновления: правка модели потребует новой сборки программ, а правка программ увезёт на сервер снимок моделей с машины сборки.

Рядом, в `moex-prodata-platform`, уже принят тот же приём для закрытого контура (ADR-0044): полная поставка образов, поставка кода поверх уже загруженного образа, один архив на перенос. Это прецедент операции. Код, скрипты и имена образов prodata этот репозиторий не импортирует и от них не зависит.

## Decision

Шаги PR-0…PR-4 из таблицы D6 уже в репозитории: образы служебного интерфейса и веб-приложения, compose, скрипты полной поставки и поставки поверх, провайдер GitLab, сверка копии моделей с контрактами образа. Отдельный репозиторий моделей в GitLab этим решением задан и ещё не выделен (PR-5). Статус остаётся Proposed: его принимает человек. Ниже — как поставка устроена. До статуса Accepted по этому тексту нельзя говорить, что рабочий сервер уже запущен.

### D1. Два канала

1. **Программы** едут Docker-образами. В образе: код `apps/` и `packages/`, контракты из `generated/contracts`, собранные страницы веб-приложения, nginx. Файлов моделей в образе нет.
2. **Модели** живут в отдельном репозитории локального GitLab. На сервере — рабочая копия в томе. Раскладка копии сохраняет `model-assets/` и `generated/`, чтобы поиск корня по файлу схемы DAMS и относительные пути в YAML не менялись.
3. В первую поставку входят служебный интерфейс, веб-приложение и сборка просмотра из тома моделей. drawDB не входит.
4. Секреты (`.env`, токены) в образ и в архив поставки не кладут. На сервере их заводят отдельно.

Обновление программ не переписывает модели. Обновление моделей не требует нового образа программ.

### D2. Поставка программ — как в прецеденте prodata

Имена этого репозитория, не prodata: тег `MODEL_TAG`, образы служебного интерфейса и веб-приложения, состояние на сервере в `airgap-state.json`.

1. **Полная поставка.** Сборка на машине с сетью и Docker. `docker save`, gzip, SHA256, манифест состава, отдельный архив файлов запуска (compose и пример окружения). На сервере: проверка суммы, `docker load`, запуск по тегу. Базовые образы (`python`, `node`, `nginx`) нужны только на машине сборки.
2. **Поставка поверх.** Когда меняется код, а [отпечаток зависимостей](#d3-отпечаток-зависимостей-и-версия) совпал с последней полной поставкой. Архив — снимок исходников и уже собранных страниц веб-приложения. На сервере `docker build` с `FROM` уже загруженной полной поставки и с `--network=none`. Снимок полный (`rm -rf` каталога кода и копирование заново), не цепочка заплаток. Основа — всегда последняя полная поставка, никогда предыдущая поставка поверх.
3. **Пакет для контура.** Один zip на перенос: полная поставка или поставка поверх, контрольная сумма, манифест, архив файлов запуска, `APPLY.md`, `apply-contour.sh`. Канонический каталог сборки — `reports/docker/` этого репозитория. На сервере архив распаковывают `unzip`, не `gunzip`.
4. **Откат.** Предыдущий тег, если образ ещё на диске. Откат поставки поверх на более старый снимок — только с явным разрешением (`APPLY_ALLOW_DOWNGRADE=1`) или ручной сменой `MODEL_TAG`.
5. Закрытый registry не обязателен. Канал «git pull и сборка на сервере» для этого контура не используется.

Первый файл compose при запуске — `docker-compose.yml` из корня поставки. Файл prod-наложения только подменяет образ уже загруженным тегом и отключает сборку на сервере.

### D3. Отпечаток зависимостей и версия

`deps_fingerprint` — SHA256 от:

- Dockerfile программ;
- срезов зависимостей всех `pyproject.toml` (`requires-python`, `dependencies`, `optional-dependencies`), без поля `version`;
- `apps/web/package-lock.json`.

Совпал с отпечатком полной поставки, которая уже на сервере, — следующая поставка кода идёт поверх. Не совпал — нужна новая полная поставка.

Номер поставки — поле `version` корневого `pyproject.toml`. Каждый пакет для контура поднимает patch (`0.1.0` → `0.1.1`). Повтор той же версии с другим `git_sha` запрещён. Скрипт сам коммит с новым номером не создаёт: номер коммитят отдельно после упаковки.

Метка на полной поставке: `moexmodel.full_version`, `moexmodel.deps_fingerprint`, `moexmodel.git_sha`. На поставке поверх добавляется `moexmodel.parent_tag`.

### D4. Поставка моделей и правки с сервера

1. На сервере отдельный шаг синхронизации: `git fetch` и быстрая перемотка вперёд из локального GitLab по токену только на чтение, затем сборка статического просмотра из этой копии.
2. Правка модели из веб-приложения идёт в GitLab через API v4: ветка, коммит, запрос на слияние. Прямой коммит в защищённую основную ветку адаптер не делает. Разбор изменения перед слиянием остаётся требованием ADR-012; сам обязательный шлюз по ADR-012 ещё Proposed и этой поставкой не закрывается.
3. Перед работой служебный интерфейс сверяет копию моделей с контрактами внутри образа (файл-маркер схемы на месте, манифест контрактов совпал). Расхождение — отказ старта, а не тихий запуск на несовместимой схеме.

### D5. Кто вызывает интерфейс, пока нет OIDC

Локальный запуск по-прежнему принимает заголовок разработчика и по умолчанию считает действующим лицом `dev`.

На рабочем сервере nginx передаёт имя пользователя доверенным заголовком (`MOEX_AUTH_MODE=trusted-header`). Это не замена OIDC. Пока входа через поставщика удостоверений нет, служебный интерфейс снаружи доступен только через этот nginx, не напрямую.

### D6. Серия правок

Одна тема на шаг. Схемы и `generated/` эта серия не меняет. PR-0 не содержит кода поставки.

| Шаг | Тема |
|---|---|
| PR-0 | Этот ADR, строка в указателе, страница `docs/user` |
| PR-1 | Адрес и порт интерфейса из окружения, режим доверенного заголовка, сверка копии моделей с контрактами образа |
| PR-2 | Провайдер GitLab в `packages/git-adapter` |
| PR-3 | Dockerfile, compose, синхронизация моделей |
| PR-4 | Скрипты полной поставки, поставки поверх и пакета для контура, цели Makefile |
| PR-5 | Порядок работы с локальным GitLab: токены, защищённая ветка, установка, обновление, откат |

Совмещённого шага «схема + данные + пересборка generated» в серии нет.

## Рассмотренные альтернативы

**1. git pull и сборка на сервере.**  
На сервере нет сети для базовых образов, pip и npm и нет полной копии этого репозитория. Отклонено как путь закрытого контура.

**2. Модели внутри образа.**  
Обновление модели становится новой поставкой программ, а на сервер попадает снимок моделей с машины сборки, а не ревизия GitLab. Отклонено.

**3. Обязательный закрытый registry.**  
Сервер не обязан уметь забирать образы с машины сборки по сети. Registry допустим позже поверх того же образа, не как единственный канал.

**4. Цепочка поставок поверх и правка файлов внутри контейнера (`docker commit`, патч только изменённых путей).**  
Удаления из git остаются в образе, слои раздуваются, основа перестаёт быть известной полной поставкой. Отклонено. Поставка поверх — снимок всего кода на последней полной поставке.

## Последствия

- Два независимых обновления: программы архивом, модели — `git fetch` из локального GitLab.
- Откат программ — загрузка предыдущего архива или смена тега. Откат моделей — ревизия Git.
- Полная поставка тяжёлая (образы с веб-приложением). Поставка поверх меньше, но требует, чтобы полная поставка с тем же отпечатком уже была загружена.
- Расхождение схемы DAMS в копии моделей и контрактов в образе ловится до приёма запросов.
- Доверенный заголовок без OIDC безопасен только пока интерфейс не торчит мимо nginx.

## Проверка

Пока статус Proposed, принятие решения отдельно от кода. Код серии проверяется так:

- `make pack-full` — архив образов, SHA256 и манифест с `deps_fingerprint`;
- `make pack-contour PARENT_TAG=<версия полной поставки>` — пакет для контура;
- `pytest tests/test_airgap_overlay.py tests/test_airgap_pack.py apps/api/tests/test_runtime.py packages/git-adapter/tests/test_gitlab.py`;
- `python -m moex_model_api.preflight` — сверка копии моделей с контрактами этого процесса.

Те же команды подтверждают поведение: поставка поверх отказывается, если отпечаток не совпал с полной поставкой; пакет для контура распаковывается `unzip` и поднимает сервисы по `MODEL_TAG`; `preflight` завершается с ошибкой, когда схема копии моделей не совпала с контрактами процесса. После PR-5 правка из интерфейса создаёт ветку и запрос на слияние в локальном GitLab и не коммитит в защищённую основную ветку.
